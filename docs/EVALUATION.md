# Evaluation plan and results log

This file is the single place where evaluation protocols are defined and where results are recorded as they are produced. **Results are only entered after the experiment has been run. Nothing here is a result unless it says so.**

## 1. Tracking accuracy (RQ1)

**Protocol**

1. Choose 20-30 frames spread across a clip, including crowded moments (corners, set pieces) and open play.
2. For each frame, annotate every visible player's feet position (click in the video), convert pixels to pitch metres using the same calibration, and record the team. Save in the `tracking.json` format with only the annotated frames.
3. Run `python -m tactics.evaluate tracking.json ground_truth.json --gate 2.0 --json results.json`.
4. Repeat with `--gate 1.0` and `--gate 3.0` to show how the conclusion depends on the tolerance.

**Metrics:** precision, recall, F1 (a detection is correct if within the gate of an annotated player after one-to-one matching), mean, median and RMSE position error in metres, team-assignment accuracy.

**Not yet available:** identity switches, MOTA and IDF1. These need ground truth with consistent ids across frames. Do not report them until implemented.

## 3. Key-moment agreement (RQ2)

**Protocol**

1. Choose 5-8 short clips (30-90 s) with a plan drawn on the board for the phase of play shown.
2. Two or three qualified coaches independently mark moments where the team's shape departed meaningfully from the plan. They do not see the tool's output.
3. Run `python -m tactics.compare` with a stated threshold and minimum duration (fix these **before** looking at the coaches' labels to avoid tuning to the answer).
4. A tool flag matches a coach label if their intervals overlap within a tolerance of 2 s. Report precision and recall of the flags against each coach and against the majority.
5. Report agreement between coaches (Cohen's kappa for pairs) so the reader knows how much agreement is even achievable.

## 4. Usability (RQ3)

**Protocol**

- 8-10 participants (players or coaches), all adults, with informed consent and approval in place first.
- Tasks, for example: set a 4-4-2, build a two-keyframe press, load a tracked replay, and say how far the back line differed from plan at a given time.
- Measure task completion, time on task and errors, then the System Usability Scale. Compare with a whiteboard baseline on the same tasks.
- SUS scoring: for each odd item subtract 1 from the score, for each even item subtract the score from 5, sum the ten values and multiply by 2.5. The widely quoted average is about 68, but treat it as context, not a pass mark.

## 5. Software quality evidence

- 39 automated tests (unit, and headless-browser smoke tests), run in CI on every push.
- Metric parity between the board and the Python tools is tested against the same hand-computed numbers.
- Screenshots in `docs/img/` are generated by the browser tests (`SAVE_SCREENSHOTS=1`), so they show the real current behaviour.

## Reporting rules

- State the clip source, camera position, resolution and licence or consent basis for every result.
- Give the exact command and settings so any result can be reproduced.
- Report failures. A recall of 0.7 with an honest explanation scores better than an unexplained 0.95.
